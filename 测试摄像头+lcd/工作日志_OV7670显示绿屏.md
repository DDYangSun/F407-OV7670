## 二、根因（按严重程度排序）

### 问题 1（致命）：使能了 DCMI 中断，但整个工程没有 `DCMI_IRQHandler`

原 `OV7670_DCMI_Init()` 末尾有：

```c
DCMI_ITConfig(DCMI_IT_FRAME, ENABLE);   // 开启帧中断
DCMI_ITConfig(DCMI_IT_OVF,   ENABLE);   // 开启溢出中断
NVIC_PriorityGroupConfig(NVIC_PriorityGroup_4);
... NVIC_InitStructure.NVIC_IRQChannel = DCMI_IRQn; ...
DCMI_Cmd(ENABLE);
```

但是 `User\stm32f4xx_it.c` 里只有 Cortex-M 的异常处理和 `SysTick_Handler`，**没有 `DCMI_IRQHandler`**。
证据（`Listings\Project.map`）：

```
DCMI_IRQHandler   0x08000243   Thumb Code   0   startup_stm32f40_41xxx.o(.text)
```

0 字节、来自启动文件，也就是 `Start\startup_stm32f40_41xxx.s` 里 `[WEAK]` 的默认处理：

```asm
DCMI_IRQHandler
...
        B       .
```

**后果：** 摄像头一开始输出帧（或 DCMI 上溢），CPU 立刻跳进这个 `B .` 死循环，再也回不来。
主循环停在那里，LCD 上就定格在当时那半帧乱数据——看起来就是"一整屏深浅绿交替"。
这也解释了为什么"没加摄像头时 LCD 是好的"：那时根本没有 DCMI 中断。

> 另外：`DCMI_Cmd(ENABLE)` 原本在 `OV7670_DCMI_Init()` 里就打开了，而 DMA 是在后面
> `OV7670DMA_DCMItoSRAM()` 才配的，中间这段 DCMI 收到的数据没人取，会直接上溢（OVR）。

### 问题 2（致命）：SCCB 引脚配错，还和 LCD 的 DC 抢 PB1

- `User\main.c` 自己的注释写着 `// PB8(SCL)+PB9(SDA)`；
- 但 `Hardware\SCCB.c` 里实际操作的是 **PB10（SCL）** 和 **PB1（SDA）**；
- 而 `Hardware\lcd.h` 里 **`LCD_DC_GPIO_PIN = GPIO_Pin_1`（PB1）**。

由此三个后果同时发生：

1. `SCCB_WriteReg/ReadReg` 每发一位都在拨 PB1，也就是在拨 LCD 的 DC 线；
2. `SCCB_ReadReg()` 读 PB1 时，引脚已被 LCD 代码配成推挽输出，读回来的永远是"自己刚写进去的电平"，`0x32`、`0x03` 的读-改-写全部是错的；
3. 如果硬件实际接的是 PB8/PB9（main.c 注释所述），那 SCCB 数据一位都没到摄像头 → `OV7670_RegConfig()` 里 170 多条寄存器一条都没生效 → 摄像头仍然是**上电默认的 YUV 4:2:2 输出**，DCMI 抓回来当 RGB565 显示，必然花花绿绿、偏色。

> **需要你确认一处：** 我按 `main.c` 的注释把 SCCB 改成 **PB8=SCL、PB9=SDA**。
> 如果你实际是接在 PB10/PB1 上，请只改 `Hardware\SCCB.c` 顶部两个宏
> （但 PB1 是 LCD 的 DC，物理上不能同时给摄像头当 SDA，必须换脚）。

### 问题 3（致命）：`LCD_ShowOV7670PIC()` 没有设置显示窗口

原函数直接 `LCD_Writ_Bus(0x2c)` 就开始灌像素：

```c
LCD_DC_Clr(); LCD_CS_Clr();
LCD_Writ_Bus(0x2c);
LCD_DC_Set();
for (i = 0; i < 120 * 160; i++) LCD_WR_DATA(Image[i]);
```

ST7735 的 GRAM 写指针是"带窗口的"，必须先 `CASET/RASET` 定好窗口，再发 `0x2C`。
不设窗口，数据就从上一次操作（`LCD_Fill`、`LCD_DrawPoint`、`LCD_ShowPicture` 等）留下的
地址指针处开始填，画面整体错位。`LCD_ShowPicture()` 里是有 `LCD_Address_Set()` 的，
唯独这个新加的刷图函数漏了。

### 问题 4（显示比例）：160 个点写进 128 列的屏

- 摄像头 QQVGA = **160×120**；
- 屏幕 `USE_HORIZONTAL 1` → `LCD_W=128, LCD_H=160`。

一行 160 个点往 128 列里写，多出来的 32 个点会折到下一行，整幅图被"拉斜"成斜条纹。
现在改成每行只取中间的 128 个点（左右各裁 16 个），画面不变形。

### 问题 5（健壮性）：初始化顺序 + 无法自检

- 原顺序是"先配摄像头、后初始化 LCD"，一旦前面死机，屏幕什么都不显示，只能靠猜；
- 现在改成"先把屏点亮刷白"，屏幕本身成了状态指示灯；
- 并新增 `OV7670_CheckID()`，上电先读 PID(0x0A)/VER(0x0B)，读不到 `0x76/0x73` 就直接刷红屏停住——
  一次性把"SCCB 到底通没通"这件事判断出来。

# 第二轮：红屏（SCCB 读不到 ID）的继续排查

> 现象：把 SCCB 宏改成实际接线 PB10/PB11 后，仍然是"白屏一闪 → 立刻红屏 → 停住"。

红屏本身是自检在起作用：它表示 **SCCB 读不到 PID=0x76 / VER=0x73**，问题被限定在"MCCB 通信"这一层，
与屏幕、与图像数据无关。

## 8.1 第二个根因：整个工程从来没有调用过 `Delay_Init()`

`System\Delay.c`：

```c
static uint32_t fac_us = 0;          // 静态初值 0
void Delay_Init(uint8_t SYSCLK)
{
    SysTick_CLKSourceConfig(SysTick_CLKSource_HCLK_Div8);
    fac_us = SYSCLK/8;
    ...
}
```

全工程搜索 `Delay_Init`，只有 `Delay.c` 里的这一处定义，**没有任何地方调用它**。
于是 `fac_us` 永远是 0，`Delay_us()` 里：

```c
uint32_t total_ticks = nus * fac_us;   // = 0
while (total_ticks > SYSTICK_LOAD_MAX) {...}   // 不进入
if (total_ticks > 0) {...}                      // 不进入 → 直接返回
```

**所有 `Delay_us()/Delay_ms()` 都是空操作。**

后果：SCCB 每一位之间没有任何间隔，SCL 周期只由函数调用开销决定（工程是 `-O0`，一次
`GPIO_WriteBit`+`Delay_us` 大约 0.4~0.6 µs）→ SCL 跑到 0.8~1.2 MHz，
**是 OV7670 SCCB 上限 400 kHz 的两三倍**，从机根本不应答，读回来就是 0xFF，于是红屏。

这也解释了为什么"单跑 LCD 一直没事"：LCD 是纯输出、软件 SPI 没有最小时序要求，
延时失效看不出来；而 SCCB 是双向握手协议，延时一失效立刻失败。顺带地，
`OV7670_Rest()` 的 100 ms 复位脉宽、`LCD_Init()` 的 120 ms 唤醒时间此前也全都没有生效。

**修复：**

1. `main()` 第一行显式调用 `Delay_Init((uint8_t)(SystemCoreClock / 1000000));`
2. `Delay_us()` / `Delay_ms()` 里加自愈保护：`if (fac_us == 0) { Delay_Init(...); }`，以后忘了调用也不会再退化；
3. SCCB 位延时保持 10 µs（约 33 kHz），稳稳低于 400 kHz 上限。

## 8.2 红屏不再是"猜"，改成把实测值打到屏上

`main.c` 里自检失败时不再单纯刷红，而是显示：

```
SCCB ERROR
PID=xx
VER=xx
LINE=x
SCL=PB10
SDA=PB11
```

其中 `LINE` 来自新增的 `SCCB_TestLine()`（先释放 SDA 读一次，再主动拉低读一次）：

| 屏幕显示 | 含义 | 下一步 |
|---|---|---|
| `PID=76 VER=73 LINE=0` | 通信正常 | 正常，会继续往下跑出图像 |
| `PID=FF VER=FF LINE=0` | SDA 空闲为高、能拉低，但摄像头不应答 | 时序/地址问题：把 `SCCB_W_SCL/SDA` 里的 `Delay_us(10)` 加大到 50 试试；仍不行则查模块供电（3.3V/2.8V）与 PWDN |
| `LINE=1` | SDA 释放后仍是低 | 没有上拉电阻 / SDA 对地短路 / 摄像头模块没供电 |

# 第三轮：画面过一段时间就定格（是不是溢出）

## 9.1 先回答 `Delay_Init()` 的形参

```c
void Delay_Init(uint8_t SYSCLK)
{
    SysTick_CLKSourceConfig(SysTick_CLKSource_HCLK_Div8);   // SysTick 计数时钟 = HCLK/8
    fac_us = SYSCLK/8;      // 1 微秒需要多少个 SysTick 计数
    fac_ms = fac_us*1000;   // 1 毫秒需要多少个计数
}
```

**形参填的是"系统主频，单位 MHz"**，本板填 `168`（也可以写成 `SystemCoreClock/1000000`）。

为什么这样：
- SysTick 是 24 位**递减**计数器，每来一个时钟减 1；
- 上面第一行把它的计数时钟设成了 `HCLK/8`，HCLK = 168 MHz 时就是 21 MHz；
- 21 MHz 意味着 **1 µs 有 21 个计数**，正好等于 `SYSCLK/8 = 168/8 = 21`；
- 于是 `Delay_us(n)` 只要把 `n*21` 写进 `SysTick->LOAD` 等它数完，就是 n 微秒。

为什么形参类型是 `uint8_t`：MHz 的数值不会超过 255（F407 最高 168/180 MHz），一个字节足够。

有什么用：**它是整个延时体系的"标定值"**。没有它（或填 0），`fac_us=0`，
`Delay_us()` 里 `total_ticks = nus*0 = 0`，两个分支都不进，函数立刻返回——
所有延时都会变成空操作。之前 SCCB 读不到 ID 就是这个原因（SCL 跑到 1 MHz，超过 OV7670 的 400 kHz 上限）。

填错了会怎样：
- 填大（比如实际 168 却填 200）：延时整体变长，SCCB 变慢但还能用，LCD 刷新变慢；
- 填小（比如填 84）：延时只有一半，SCCB 会重新超速，可能又读不到 ID；
- 填 0：延时全部失效。

推荐写法（不依赖具体主频，即使 HSE 不起振退回到 HSI 16 MHz 也正确）：

```c
Delay_Init((uint8_t)(SystemCoreClock / 1000000));
```

另外我在 `Delay_us()` / `Delay_ms()` 里加了保护：`if (fac_us == 0) { Delay_Init(...); }`，
以后即使忘了调用也不会再退化成空操作。

## 9.2 画面定格是不是溢出？—— 大概率是 DCMI 上溢（OVR）

DCMI 的接收路径是：`PCLK 采样 → DCMI 内部很小的 FIFO（4×32bit） → AHB/DMA → SRAM`。
PCLK 一直在往里灌，DMA 只要晚一步取走，FIFO 就溢出。

本工程里 CPU 用**软件 SPI 刷屏**，一帧 128×120 要 40 ms 以上，几乎把总线和 CPU 占满。
在这段时间里，DMA 偶尔抢不到总线，FIFO 就会溢出：

1. OVR 标志置 1；
2. **DCMI 硬件会自动把 CAPTURE 位清零，采集就此停止**；
3. DMA 再也收不到数据 → TC 中断不再产生 → `LCD_ShowReady` 永远是 0；
4. 主循环一直在转，但没有新帧可画 → **画面定格在最后一帧**。

所以"跑一段时间才停"完全说得通：需要 CPU 占用和 PCLK 正好撞在一起才会溢出一次，而溢出一次就永久停。

其他可能（按概率）：
- DMA 传输错误（TEIF/FEIF）把 stream 直接关掉；
- 摄像头模块供电不足或发热（OV7670 + 屏背光同时工作电流不小，尽量别只靠 ST-Link 供电）；
- 程序 HardFault 卡死。

## 9.3 这一轮加了什么

1. **屏幕下方多了统计信息**（画面只占 y=0~119，下面 40 行是空的）：

   ```
   F00012D00012
   O003R02
   ```

   | 字段 | 含义 |
   |---|---|
   | `F` | DMA 收到新帧的次数 |
   | `D` | 真正刷到屏上的帧数 |
   | `O` | DCMI 上溢(OVR)次数 |
   | `R` | 兜底重新武装采集的次数 |

2. **自愈逻辑**：连续约 500 ms 没有新帧，就 `StopGetPicture → 重新初始化 DMA → GetPicture`，
   不管停的原因是上溢、DMA 错误还是别的，都能自己爬起来（`R` 会 +1）。

3. **OVR 计数**：主循环里轮询 `DCMI_FLAG_OVFRI` 并清除、计数。

## 9.4 怎么用这四行字判断

| 看到的现象 | 结论 | 下一步 |
|---|---|---|
| 画面定格，但 `F`、`D` 还在涨 | 采集正常，问题在显示 | 基本不会发生，先看下一条 |
| 画面定格，`D` 不涨、`F` 也不涨，文字还在变，`O` 变大 | **就是 DCMI 上溢** | 见 9.5 |
| 画面定格，`D/F` 不涨，`O` 不变，`R` 在涨 | 不是上溢，是 DMA/摄像头掉线 | 见 9.5 第 3、4 条 |
| 文字也停止变化 | 程序本身卡死（HardFault） | 需要接调试器看 PC |
| `R` 一直在涨、画面一会儿有一会儿没有 | 自愈在反复触发 | 说明底层确实不稳定，按 9.5 根治 |

## 9.5 要根治，按这个顺序试

1. **先降 PCLK**：`OV7670_MCLK_start()` 里把 `RCC_MCO1Div_2`（8 MHz）改成 `RCC_MCO1Div_4`（4 MHz），
   数据率减半，DCMI 压力直接小一半。如果改完 `O` 不再增长，就确认是带宽问题。
2. **减少 CPU 占总线**：现在软件 SPI 刷一帧 40 ms 以上，是最大的干扰源。
   正解是把 LCD 改成硬件 SPI + DMA，CPU 只在 DMA 完成中断里发一个开始信号。
3. **改成快照模式**：`DCMI_CaptureMode_SnapShot`，采一帧就停，画完再开下一帧，
   "采的时候不画、画的时候不采"，彻底避免两者抢总线（帧率会降到 10 帧左右，但绝对稳定）。
4. **提高 DMA 优先级**到 `DMA_Priority_VeryHigh`；确认摄像头和板子用稳定 3.3 V 供电。
